# Retrieval Benchmark: TF-IDF vs Dense Embeddings

Generated by `scripts/benchmark_retrieval.py --report`. Re-run to reproduce.

## Question

The deployed pipeline retrieves context with a pure-Python TF-IDF index because Vercel serverless functions cannot carry PyTorch. Does lexical matching miss the semantic nuance in how people describe distress? This benchmark compares the **unmodified production retriever** against a small dense model on the **same corpus**.

## Setup

- Corpus: 45 dataset passages + 5 topic keyword strings (identical to what production indexes)
- Queries: 47 labelled messages — 18 lexical (share vocabulary with the dataset), 25 paraphrase (same intent, no keyword overlap), 4 Hinglish
- Retrievers: `tfidf` = production `retrieve()`; `dense` = all-MiniLM-L6-v2 cosine; `hybrid` = reciprocal-rank fusion of both
- Metric unit: the **topic** of each retrieved passage (top-5), since the prompt only needs the right topic

## Interpretation

- On **lexical** queries TF-IDF gets 17/18 and dense gets 17/18: when users echo the dataset's vocabulary, lexical matching is sufficient.
- On **paraphrase** queries TF-IDF gets 4/25 versus dense 14/25 and hybrid 8/25. This is the gap the benchmark was designed to expose: dense embeddings recover intent that shares no words with the corpus.
- **Hinglish** is weak for both: MiniLM is English-only and the corpus contains no Hindi, so the fix is data (add Hinglish user_signals), not the retriever.

## Decision

TF-IDF stays in production for now because the serverless memory limit rules out PyTorch, and the lexical subset shows it is adequate for the common case. The paraphrase gap is real and is addressed in two steps:

1. **Cheap, now:** add paraphrased `user_signals` to `data/dataset3.json` so TF-IDF's topic-keyword boost catches indirect phrasings (the misses table above is the backlog).
2. **Later:** move dense retrieval to a hosted embedding API (no local model), gated by the same benchmark so the change is measured, not assumed.
